## 2024-03-15 - Redundant serialization and heap allocations in TTL -> LRU promotion
**Learning:** In `CacheManager::get_embedding` and `CacheManager::get_edge_relationship`, when promoting an entry from the `TtlCache` (which returns a reference) to the `LruCache` (which takes owned data), we were previously deserializing the `TtlCache` entry's byte slice into a struct, and then re-serializing the struct back into a byte slice to pass into `LruCache::put`. Additionally, we were needlessly cloning the `cache_key`. In `LruCache::get` we can see it returns an owned `Option<CacheEntry>`, which means the `entry.value` doesn't need to be cloned again when returned to the caller.
**Action:** When promoting from `TtlCache` to `LruCache`, clone the underlying `entry.value` (the serialized byte slice) directly, completely eliminating the redundant `bincode::serialize` step and the associated heap allocation. Additionally, pass the `cache_key` by value into `LruCache::put` since it is not needed afterward. When returning from `LruCache::get`, we can move `entry.value` because the entry is already owned.
